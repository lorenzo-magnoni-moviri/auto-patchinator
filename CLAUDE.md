# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An interactive CLI that reads a monthly Splunk patch-wave Excel plan, extracts the Splunk BB team's steps (rows where `Gruppo_referente` is one of `--team-filter`'s values — `"AOM Sky CSO"`, `"AOM Splunk Broadband"`, or `"Splunk Broadband"`; the wave's author doesn't use a single consistent label month to month) in dependency order, resolves them to per-node stop/disable/enable/start action sequences, and walks an operator through confirming/running/skipping each one over SSH (via a PAS/CyberArk gateway). Python 3.10+, deps: openpyxl, PyYAML, paramiko.

## Commands

```bash
# Setup (venv at .venv already exists)
source .venv/bin/activate
pip install -e .

# Run - LIVE by default (real SSH, prompts for credentials, shows MODE banner).
# --excel and --inventory are both optional (see cli.py: _prompt_for_excel_path,
# _resolve_inventory_path) - the PAS/CyberArk gateway always comes from hosts.yaml's
# pas_gateway, there's no CLI override. Group->host mapping is read directly from the
# Excel's 'List Host NO IT' sheet, cross-referenced against the inventory. The 'Plan'
# and 'List Host NO IT' sheet names aren't overridable either - a workbook that doesn't
# match the expected format (see excel_parser.py/wave_mapping.py's sheet-name fallback
# matching) fails with an actionable error instead of silently guessing.
auto-patchinator run --excel <plan.xlsx> --inventory inventory/hosts.yaml

# Simulate only (no SSH) - for testing plans end to end
auto-patchinator run ... --dry-run

# Verify SSH connectivity to all inventory nodes
auto-patchinator check-connectivity --inventory inventory/hosts.yaml
```

```bash
# Tests (pytest; install test deps with: pip install -e ".[test]")
python -m pytest            # whole suite
python -m pytest tests/test_run_plan.py -k captain   # single file / test
```

No linter is configured. The unit tests cover the plan pipeline and pure helpers; the interactive flow and SSH layer are exercised via dry-run mode end to end.

## Architecture

Data flows through a strict pipeline, assembled in `cli.py:cmd_run`:

1. **`plan/excel_parser.py`** — reads the Excel "Plan" sheet into `RawStep` rows (header names come from the sheet verbatim, including the "Dependancy" typo).
2. **`plan/action_mapping.py`** — filters to team rows and regex-parses the verb (stop/start) and group numbers out of the free-text `Nome` column (the `Tipo` column is empty for Splunk rows). Rows it can't confidently parse are returned separately and flagged for manual review — never silently guessed.
3. **`plan/dependency.py`** — Kahn's-algorithm ordering. Dependencies pointing outside the team's own step set (other teams' steps) become `external_dependencies`, which surface as a manual "confirm the other team finished" action at run time.
4. **`plan/wave_mapping.py` + `config/inventory.py`** — `wave_mapping.py` reads the group→hostname mapping directly from the Excel's "List Host NO IT" sheet and cross-references it with the static inventory (`hosts.yaml`) to filter to our team's hosts. The inventory (hostname→role/site/manual-identity exceptions) doesn't change month to month.
5. **`plan/run_plan.py`** — combines the above with `actions/sequences.py` into `RunStepPlan`s: `pre_group_actions` / `per_host_actions` / `post_group_actions`. Group-level actions are deduped per role (or per overridden host), not by sequence equality.
6. **`preflight.py`** — pre-patch "pretest", run automatically before every LIVE `run` (skipped for `--dry-run` — its whole point is "no SSH at all"). Scoped to exactly the hosts the resolved plan touches (`plan_hostnames`), not the whole inventory: SSH connectivity for splunk then root identity (`executor/connectivity.py`, shared with `check-connectivity` itself — one implementation, not two; root is provisioned per-request in this environment, so a FAIL there is routine, not necessarily a problem); if the plan touches any `search_head_stretched` host, a further splunk-identity-only connectivity check against the *rest* of that cluster (`Inventory.stretched_sh_hostnames()`, both sites, minus whatever the plan-hosts check already covered) — captain transfer/revert (still manual) already instructs the operator to touch every member cluster-wide, so this matters even before that step is automated; root isn't needed for it. Then — only if Splunk API credentials are configured (`SPLUNK_API_USER`+`SPLUNK_API_PASSWORD` in `.env`; gracefully skipped otherwise, including when only a bare `SPLUNK_API_TOKEN` is set) — per distinct search-head role present (`search_head_stretched` and `search_head_simple` are separate Splunk search head clusters, checked separately): runs `splunk show shcluster-status --verbose -auth "<user>:<password>"` and `splunk show kvstore-status --verbose -auth "<user>:<password>"` as the splunk identity over the same SSH session (no root needed — the Splunk admin credentials authorize this, not the OS identity), parsing the CLI's `--verbose` text output (a `key : value` table using the same raw field names as the REST API, e.g. `dynamic_captain`, `label`) for the current SHC captain, dynamic-vs-static election, and each search head's own local KV store status. The admin password is never sent as literal command text — `SSHConnection.run_plain_with_secret` (`executor/ssh.py`) sets it via a redacted shell-variable send first, so it never appears in `logs/run-*.log`. (2026-09-22: this redaction originally only covered the *send* - the `read_until()` right after it captures the PTY's own local echo of that same line, which needs `sensitive=True` too, or the secret leaks via the read side instead; found live, fixed - see TODO.md.) Never aborts the run — failures print clearly and the operator still decides at the existing "Proceed with this plan?" prompt.
7. **`runner/controller.py`** — the interactive loop. Each step is run in one of three operator-chosen modes (asked per step; capital `A`/`T`/`M`, or `--full-auto-mode` for automatic specifically, locks that mode in via `self._locked_mode` so the question isn't asked again for the rest of the run): *automatic* (one line per action, pauses only on manual confirmations and failures), *task-by-task* (run / mark-done-manually / skip / back / jump / quit per action), or *manual guide* (`m`: executes nothing — presents each task's command, host, user + su command, and rationale; ENTER confirms it done, `l` lists all tasks, no ssh commands printed since the team connects via WinSSH). Hosts sharing an identical remaining task list + su hint (`_host_profile`/`_build_host_groups`) are shown once and confirmed as one batch instead of once per host, with an `i` fallback to per-host confirmation. Literal commands (su hints, task `run:` lines, and any 3+-space-indented line inside a `MANUAL` action's note - see `captain_transfer_static`/`captain_revert_dynamic`) are highlighted in cyan (`_guide_what` returns `(line, is_command)` tuples) so they stand out from surrounding prose. Failures show a red block + retry menu in all executing modes (`term.py` has the ANSI color helpers, auto-disabled when not a tty). The terminal's visible screen (not scrollback) is cleared at the start of every step via `term.clear_screen()`. Persists state after every transition. Automatic mode (`_run_automatic`) reuses one SSH connection per (host, identity) across a host's whole per-step action list (`_HostConnections`) instead of reconnecting for every action, and never carries a connection into another step (a host may be rebooted by another team's OS-patch action between a step's stop and start halves); `--max-parallel-hosts N` (default 3; pass 1 for the old fully-sequential behavior) runs that many hosts' action lists concurrently via `ThreadPoolExecutor`, with console output/state saves serialized (`_console_lock`/`_state_lock`) and a shared `threading.Event` so a quit chosen from one host's prompt stops the others before their *next* action without killing anything mid-SSH. A per-host confirmation prompt (e.g. `_confirm_kvstore_clean_auto`) holds `_console_lock` for its whole `input()` call, so while one host is waiting on an answer, other hosts' SSH work keeps running but their console output (including their own next prompt) queues behind it — expected, not a hang. In that same concurrent path, a slow action used to print nothing at all between its `...` line and its result — indistinguishable from a hang (found live, 2026-09-22, when a search-head-cluster captain's `stop_splunk` took ~4m45s with zero output and prompted a risky manual `splunk stop` on the real host - see TODO.md); `_heartbeat` (a context manager wrapping that branch of `_attempt_with_retry`) now prints a new `still running (Ns)` line every 30s while the action is still in flight. Pre-/post-group actions always stay sequential. Task-by-task and manual guide are unaffected (still one connection per action, no concurrency).
8. **`state/`** — JSON run state under `state/`; on startup an incomplete run is detected and offered for resume. Only one run's state file is kept on disk at a time (`store.prune_other_states`, called from `cli.py` right after the active run's state is decided/saved). **`reports/report.py`** writes a markdown report at the end (not pruned).

### Action model (`actions/`)

- `types.py`: `Action` has a kind (`PLAIN` shell command, `INTERACTIVE` expect-script, `MANUAL` operator step, `WAIT` fixed-duration sleep, `CLUSTER_WAIT` poll-until-healthy-or-timeout, `STREAMSETS_PIPELINE` POST start/stop then poll status until target-or-timeout) and an identity (`splunk` or `root`). Validation is in `__post_init__`.
- `sequences.py` is the domain knowledge core. Each role (deployer, indexer, forwarder, search_head_simple, search_head_stretched) exposes **separate STOP and START halves** — the Excel models "Stop Group N" and "Start Group N" as independent steps because OS patching happens between them, outside this tool. Each half has pre-group / per-node / post-group phases. Both search-head roles' start halves end with `wait_for_shcluster_member_healthy` (a `CLUSTER_WAIT` action) — polls this host's own search-head-cluster membership via `splunk show shcluster-status --verbose -auth` (parsed by `executor/splunk_cli.py`) until it's healthy or times out; runs as the splunk identity (no root needed — Splunk admin credentials authorize it), and is forced manual when Splunk API credentials aren't configured (`runner/controller.py`'s `is_forced_manual`).
- `HOST_OVERRIDES` (keyed by hostname) replaces the role sequence entirely for special hosts. `prdmilbbspkfw02`'s stop half runs five `STREAMSETS_PIPELINE` stop actions (`STREAMSETS_PIPELINES` in `sequences.py` — RDK/ODP/ODP PODS/RDKV/ATD, real pipeline IDs) before the Splunk stop, and its start half runs the same five as `STREAMSETS_PIPELINE` start actions after the Splunk start — each is `POST .../{stop,start}?rev=0` via the StreamSets Data Collector REST API (`executor/streamsets_api.py`), then polls `.../status?rev=0` until the target status (`STOPPED`/`RUNNING`) is reached (the stop/start call itself only signals the transition; verified live, ~4.6s to settle for an idle pipeline — 5s poll / 90s timeout). Forced manual when `STREAMSETS_API_USER`/`STREAMSETS_API_PASSWORD` aren't set in `.env`. `MANUAL_ONLY_IDENTITIES` lists hosts where an identity can't be used over SSH (CyberArk-GUI-only); the controller forces those actions to manual.
- Indexers use a different Splunk binary path (`/splunkdata/splunk/bin/splunk` vs `/opt/splunk/bin/splunk`) and a different su command.

### SSH layer (`executor/ssh.py`)

Everything runs in one persistent PTY shell session per (host, identity) — not one-shot `exec_command` — because the `sudo su -` step and some commands prompt interactively. The PAS gateway login encodes the target identity in the username (`<user>@pas.prd.spk[.root]@<host>`); after login it still `su`s into splunk/root with the same password. Command completion/exit codes are detected via a `PS1` marker + `AP_EXIT_CODE` echo protocol. `DryRunConnection` implements the same interface and is what `--dry-run` runs use. Every run appends a DEBUG audit log (actions, operator choices, raw SSH sends/reads with passwords redacted) to `logs/run-<run_id>.log` via `logging_setup.py`, which also prunes `logs/` down to the 3 most recently modified files after each setup call.

## Invariants and cautions

- **Never hardcode the Splunk admin password** (used by `bootstrap shcluster-captain -auth admin:<password>`) anywhere in this repo. Search-head-captain transfer/revert are currently manual steps (cluster-wide scope, host choice, and credential handling are why) — automating them is a tracked short-term goal, not a permanent rule (see TODO.md's "Automate SH captain transfer / revert"); until that lands, keep them manual, and any automation must still keep a manual fallback and never touch the Splunk admin password directly. Same rule for the reserved `SPLUNK_API_TOKEN`/`SPLUNK_API_USER`/`SPLUNK_API_PASSWORD` env vars (`credentials.py:load_splunk_api_credentials`) — `.env` only, never source or commit history, never printed/logged (`SplunkApiCredentials.__repr__` redacts them) or sent over SSH as literal command text (`SSHConnection.run_plain_with_secret` redacts it in the audit log too). Now actually consumed by `preflight.py` (the pretest's captain/election/KV-store checks, run via `splunk show ... -auth`) — those checks are entirely skipped, not degraded, when these vars aren't set. Same rule again for `STREAMSETS_API_USER`/`STREAMSETS_API_PASSWORD` (`credentials.py:load_streamsets_api_credentials`), consumed by `STREAMSETS_PIPELINE` actions on `prdmilbbspkfw02` — same `.env`-only, never-literal-in-a-command, redacted-in-the-audit-log treatment via `run_plain_with_secret`.
- `*.xlsx` files are gitignored because the plan contains sensitive data; so are `state/` and `reports/`. Don't commit or echo their contents.
- The start sequence order is `enable boot-start` → `daemon-reload` → `start`. A systemd override (drop-in) file now holds the node-specific customizations, so `enable boot-start` regenerating the unit from a template no longer loses anything — there's no backup/restore-the-unit-file step anymore.
- Search-head-stretched's start sequence cleans the KV store *before* starting Splunk, not after (`enable boot-start` → `daemon-reload` → `clean_kvstore` → `start`) — the KV store is cleaned while Splunk is still down. In automatic mode, the operator is asked once per run, the first time this action is reached (`runner/controller.py`'s `_confirm_kvstore_clean_auto`, `self._kvstore_clean_decision`), whether to actually clean it — not once per search head, since there's no reason to ask the same question separately for every host being started together; the single answer applies to every subsequent `clean_kvstore` for the rest of the run. Skippable when the downtime was too short for the local copy to have gone stale; the default (blank input) keeps today's always-clean behavior. Task-by-task and manual guide modes are unaffected — the operator already controls every action there.
- The sudo/su password-prompt regex and PTY marker protocol in `ssh.py` are verified working against the real prod PAS gateway (root identity, 2026-07-03 — see `TODO.md`/`DOCUMENTATION.md` §13 for the exact findings); a new environment/banner variant could still need adjustment.
- Actions are meant to be idempotent; the controller re-presents non-SUCCESS/SKIPPED actions on resume.
- The tool runs natively on Windows too (no WSL needed) — there's no POSIX-only code (`pty`/`fcntl`/`termios`/`os.fork` etc.) anywhere, and every SSH command is a string addressed to the *remote* Linux hosts, so it's irrelevant to the local OS. Keep it that way: avoid introducing local shell-outs or POSIX-only stdlib calls (see `DOCUMENTATION.md`'s "Running on native Windows" for the current setup differences, which are CLI-invocation-only, not code-level).
